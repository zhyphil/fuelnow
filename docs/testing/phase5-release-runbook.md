## 发布顺序

1. 保留旧版本和配置，先验证备份可恢复到独立数据库；定义当前 Beta 允许的错误率、延迟、同步延迟与观察窗口。不要用小样本本机 p95 当线上承诺。
2. 在测试环境应用本次迁移并验证新旧应用兼容性。应用账号与迁移账号分离；不在应用启动时自动改 schema。
3. 真实来源采集/投影后验证四服务及两国代表站点，执行价格与坐标审计；空库、全 Unknown、陈旧数据不算通过。
4. 跑完整质量、原生配置、容器与实际设备流程；核验 API 网关日志不包含搜索坐标，验证告警接收。
5. 经用户明确批准后，将同一镜像 digest 部署到目标；移动端更新使用正确 API 环境和兼容契约，不混用测试/生产数据。
6. 观察设定窗口内错误、延迟、空结果和同步指标，形成发布记录。任一关键门槛无证据即停在测试阶段。

## 回滚决策

| 故障                   | 优先动作                                                                    | 禁止的捷径                            |
| ---------------------- | --------------------------------------------------------------------------- | ------------------------------------- |
| 新应用导致错误/超时    | 暂停晋级，切回已验证旧镜像/配置并复验核心查询                               | 不按浮动 latest 猜测旧版本            |
| 新数据快照异常         | 暂停对应同步，恢复已验证 last-known-good 数据版本或明确显示不可用           | 不把陈旧值标为 Live，不静默清空业务表 |
| 数据库迁移不兼容       | 停止发布；优先前向兼容修复，必要时经批准进入恢复流程                        | 不自动反向运行 SQL 或覆盖数据库       |
| 必须恢复备份           | 先恢复到隔离实例，验证迁移/数据一致性；确认切换方案与可接受数据损失后再切换 | 不直接覆盖当前库，不未经授权删除原库  |
| 原生权限/签名/SDK 错误 | 停止分发，保留证据并构建修复安装包                                          | 不假设 JS 热更新可撤销原生权限        |

回退后重新检查真实站点、来源更新时间、错误/延迟和通知状态，再由负责人确认恢复。不要在故障日志中复制用户起点、完整请求 URL 或密钥。
